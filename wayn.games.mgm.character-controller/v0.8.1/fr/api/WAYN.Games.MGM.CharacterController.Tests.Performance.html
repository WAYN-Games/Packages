    FrameBudgetTestBase

    PERF-4 (Mode B — architecture §3.2.2) shared body for the 30 000-character frame-budget gates that back (or refute) the "30 000 characters @ 60 fps" store claim (DOC-2). PERF-4 is split into two honest variants that share this base and differ ONLY in whether rendering is folded into the measured frame time:

    • PERF-4a — simulation (SimulationFrameBudgetTests): runs headless (-nographics, forge default), so Measure.Frames times the CPU simulation loop with rendering EXCLUDED. This is the sub-claim number.
    • PERF-4b — full loop (RenderFrameBudgetTests): runs with a real graphics device (-force-d3d11, via forge test … --graphics) and a runtime camera framing the population, so the measured frame time INCLUDES render + present. This is the number a customer reads as "30 000 @ 60 fps".

    Each variant SELF-GATES on the graphics device (RequiresGraphicsDevice vs SystemInfo.graphicsDeviceType) and Assert.Ignore(string)s when the run is in the wrong mode — so one forge test --platform playmode asserts the sim number while the render test ignores, and one forge test --platform playmode --graphics asserts the render number while the sim test ignores. Neither variant is a real IL2CPP player build; even the -force-d3d11 offscreen render is closer-but-not-equal to a standalone Player (the truest number is a shipped build).

    Grounded AND moving precondition (director directive 2026-07-17). Before measuring, this base waits until the spawned population is at STEADY STATE: every character is grounded (Ground) AND at least MinMovingFraction of them are moving (planar speed > MinPlanarSpeed). Movement is BAKED into the BotCharacterPerf prefab (SimpleCharacterBotAuthoring.Move, seeded onto SimpleCharacterInput at bake time and carried through the spawner's Instantiate by the IncludePrefab query in SimpleCharacterBotBakingSystem), so the spawned population self-locomotes from the first tick with no runtime input write — the number reflects the real working scenario (active locomotion + physics + render), not an idle/settling transient. A failure to reach steady state inside the timeout fails loudly, so a stale/idle measurement can never be recorded.

    Claim linkage / clean-room canon (ADR-4). The median-≤-16.67 ms assertion is made ONLY on the clean-room reference machine (ReferenceMachineName, or forced via the ReferenceMachineEnvVar env var). On every OTHER machine the test still runs the full workload and logs the number, but replaces the assertion with an explicit Assert.Ignore(string). A breach on the reference machine REMOVES/relabels the marketing claim (DOC-2 re-spec, new PR) and never blocks the merge — PERF-4 gates the claim, not the merge.

Grid derivation from N (per §3.3): columns = ceil(sqrt(Count)); rows = ceil(Count / columns); spawn exactly Count entities (last row partial — NOT columns*rows rounded up), using the AUTHORED GridSpacing, centered on the spawner origin (LocalToWorld.Position).     RenderFrameBudgetTests

    PERF-4b — the 30 000-character FULL-LOOP frame budget (rendering INCLUDED). Runs with a real graphics device under -force-d3d11 (run with forge test --platform playmode --graphics) and creates a runtime camera + light framing the population, so Measure.Frames times the full player loop: simulation PLUS the character render path PLUS present. This is the number a customer reads as "30 000 @ 60 fps" — it is the one PERF-4 must be adjudicated on. The BotCharacterPerf render path is Entity Graphics: a baked MeshRenderer becomes RenderMeshArray + MaterialMeshInfo drawn by the pure-ECS instanced batch renderer (no per-character companion GameObject), so the render cost at 30k is the EG cull/batch/submit + present cost; that is the honest point.

    Self-gates via RequiresGraphicsDevice = true: under the headless -nographics default this test Assert.Ignores (a headless run cannot measure render), so run it explicitly with --graphics. Even -force-d3d11 offscreen render is closer-but-not-equal to a real IL2CPP Player build — the truest number is a standalone build. The median-≤-16.67 ms assertion is made on the clean-room reference machine only (ADR-4).

    SimulationFrameBudgetTests

    PERF-4a — the 30 000-character SIMULATION frame budget (rendering EXCLUDED). Runs headless under -nographics (the forge default; run with forge test --platform playmode), so Measure.Frames times the CPU simulation loop only — no GPU, no present. This is the honest simulation sub-claim: what the character-controller sim costs per frame at 30k, NOT a rendered fps. For the full-loop number a customer reads as "30 000 @ 60 fps", see RenderFrameBudgetTests (PERF-4b, --graphics).

    Self-gates via RequiresGraphicsDevice = false: if a real graphics device is present (a --graphics run) this test Assert.Ignores so render work is never folded into the sim number. The full workload (spawn 30k, grounded+moving steady state, measure) still runs; the median-≤-16.67 ms assertion is made on the clean-room reference machine only (ADR-4).

    SimulationFrequencyMatrixTests

    Sim-rate × population cost matrix (EditMode, characterization — NOT a gate). Sweeps the character count {1, 100, 1000, 10000, 20000, 30000} against the simulation frequency {20, 30, 50, 60} Hz and records, for each cell, the cost of ONE 60-fps-cadence simulation-path frame at that rate and population. It answers "how does the per-frame simulation cost scale with sim frequency and crowd size?" — the question behind the 30 000 @ 60 fps claim once the sim runs at a real 60 Hz.

    Metric per cell — sim-path ms per 60 fps frame (render EXCLUDED). Each measured frame advances a fixed 1/60 s of world time (the 60-fps render cadence) and runs only the simulation path (AdvanceOneSimulationPathTick() = Initialization + Simulation groups, no presentation/render). At sim rate F the FixedStepSimulationSystemGroup runs F/60 fixed ticks per frame (physics + locomotor over the whole population), so the cell cost rises with F. The figure is directly comparable to the 16.67 ms 60-fps budget (the simulation share of it). Because rendering is not capped in the shipped scenario, a frame rendered faster than 60 fps carries fewer than F/60 ticks and costs less — the 60-fps cadence here is the reference the claim is stated at.

    Efficiency: the expensive spawn+settle is paid ONCE per count and reused across all four frequencies (the sim rate is re-applied between measurements via the FixedStepRate singleton, which ApplyFixedStepRateSystem pushes onto the group each frame). Mean is the headline (it averages the fixed-tick beat over frames); median is logged alongside. This suite does not assert a budget — it records the surface for the director / DOC-2. The only hard precondition is that the population settles grounded, so a still-falling measurement can never be recorded.

    SimulationMemoryTests

    Simulation-path MEMORY ALLOCATION measurement (EditMode). MEASURES ONLY — it does not gate. For each character count {1, 100, 1000, 10000, 20000, 30000} it spawns and settles the population, then measures the managed heap bytes allocated per simulation-path tick (physics + locomotor, presentation excluded) and records it as a SimAllocBytes_{n} sample group in bytes per tick.

    Counterpart to SimulationFrequencyMatrixTests (which measures the TIME cost surface): that suite answers "how fast is a frame", this one answers "how much does the sim path allocate". Neither asserts a budget — they are characterization surfaces for the perf report, not pass/fail gates. The one hard precondition here is the same as everywhere in this fixture: the population must settle grounded, so a still-falling measurement can never be recorded.

    Method — byte-exact, no instrumentation in the counter span. Allocation is measured with GetAllocatedBytesForCurrentThread() (thread-local, so a background editor task on another thread cannot pollute it) captured AROUND a raw window of WAYN.Games.MGM.CharacterController.Tests.Performance.SimulationMemoryTests.AllocWindowTicks sim-path ticks — no Measure.* instrumentation inside the window, whose own per-iteration bookkeeping would otherwise be counted as sim allocation. Two windows are sampled and the larger reported, so a deterministic per-tick allocation (which repeats in both) is never under-reported. A managed allocation on the sim main thread shows up here as a non-zero B/tick figure; a Burst-clean sim path reads 0.

    SpawnCapacityTests

    PERF-1 correctness precondition: request N via the non-interactive spawn seam, settle, then assert exactly N characters exist, each in ground contact, none below the floor. This is the spawn-count/settle setup that the PERF-2…5 measurements later reuse over the same PerfSpawner surface (architecture §3.2.3, §4 PERF-1 row).

    Two tiers are pinned here: the fast N = 100 tier and the capacity-raise N = 30 000 tier (perf-raise-scene-capacity-30k / perf-verify-30k-settles-grounded). Both assert the identical invariant via AssertExactlyGroundedNoneBelowFloor(int, bool, int, float).
