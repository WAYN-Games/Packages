    Samples

    This page lists all samples included with the MGM Character Controller and provides a recommended study order.

    SinglePlayerSample
    Teaches Complete state machine with five states, transitions, input handling, camera setup, and profile configuration
    Difficulty Beginner to intermediate
    Setup time 5 minutes (see Quickstart)
    Dependencies Unity Input System, Cinemachine

    What It Contains

    The sample provides a full reference implementation of a third-person character controller:

    • 5 states: Idling, Moving, Jumping, Falling, Sliding
    • 17 transitions: All valid state-to-state transitions with priority ordering
    • 3 behavior structs: Reusable gravity, horizontal locomotion, and jump-arc logic shared across states
    • Input handling: Camera-relative movement with jump trigger accumulation
    • Profile: Tunable walk/run speed, acceleration, jump arcs, gravity, and terminal velocity
    • Prefabs: Character (Locomotor + Model) and Player (Camera + Input)
    • Assets: Pre-configured profile and input ScriptableObjects
    • Scene: A ready-to-play playground (Scenes/SinglePlayerSample.unity) with stairs, slopes, conveyors, elevators, bridges, and rotating platforms

    Key Files - Study Order

    Read the sample code in this order to build the mental model (all paths relative to Scripts/SimpleCharacter/):

    Order File What It Teaches
    1 Runtime/SimpleCharacterStateMachine.cs The anchor struct - [LocomotionStateMachine] attribute triggers source generation
    2 Runtime/Data/SimpleCharacterInput.cs Input struct with continuous (Movement, IsSprinting, IsJumping) and trigger (JumpTrigger) fields, plus accumulation in ApplyInputsToCharacter
    3 Runtime/Data/SimpleCharacterProfile.cs Profile struct composed of per-state sub-profiles (Moving.Profile, Falling.Profile, Jumping.Profile) plus AirControlFactor
    4 Runtime/Data/SimpleCharacterStateData.cs Per-state persistent data (JumpData with jump count and apex timer)
    5 Runtime/States/Idling.cs Simplest state - zeros velocity on enter, empty integrate
    6 Runtime/States/Moving.cs Walk/run speed selection and horizontal acceleration via HorizontalLocomotionBehavior
    7 Runtime/States/Falling.cs Gravity with terminal velocity via GravityBehavior; rotates to face input with no horizontal acceleration
    8 Runtime/States/Jumping.cs Air control (HorizontalLocomotionBehavior scaled by AirControlFactor) + jump arc via JumpBehavior
    9 Runtime/States/Sliding.cs Gravity-driven sliding on steep slopes, reusing GravityBehavior
    10 Runtime/States/Behaviors/ GravityBehavior, HorizontalLocomotionBehavior, JumpBehavior - reusable behavior structs states compose
    11 Runtime/States/Transitions/ 17 transitions split across From*.cs / To*.cs files, with [LocomotionTransition] and [EvaluateBefore] for priority ordering
    12 Runtime/ReorientGravityToContactSurface.cs + Runtime/System/ReorientGravityToContactSurfaceSystem.cs Opt-in gravity reorientation to the contact surface (wall-walking / gravity pads)
    13 Authoring/SimpleCharacterPlayerInputAsset.cs Camera-relative input reading from the Player GO prefab's camera
    14 Authoring/SimpleCharacterProfileAsset.cs Designer-facing jump parameters converted to runtime physics values at bake time

    Things to Try

    After running the sample, try these modifications to deepen your understanding:

    1. Change movement speed - Open the SimpleCharacter Profile asset and modify Moving > WalkSpeed / RunSpeed. Notice how the profile is baked, so you need to re-enter Play mode.
    2. Enable double jump - In the profile asset, add a second entry to the Jumps list. JumpBehavior already supports chained jumps via StateData.JumpData.JumpsCount.
    3. Disable air control - In the profile asset, set AirControlFactor to 0. The character will maintain its launch velocity with no air steering.
    4. Add debug visualization - Select the character entity in the sub-scene and add a LocomotionDebugConfigAuthoring component. Enter Play mode and observe contact points and movement paths in the Scene view.

    FlyCamSample
    Teaches Minimal single-state fly camera, gravity-free movement, split entity/camera rotation, collision handling without ground contact
    Difficulty Beginner
    Setup time 5 minutes
    Dependencies Unity Input System

    What It Contains

    A first-person fly camera controller for navigating test scenes. The camera floats freely without gravity, slides along obstacles, and uses mouse look for rotation.

    • 1 state: Flying (always active — no transitions needed)
    • No gravity: Zero vertical acceleration, ground snapping disabled
    • Split rotation: Entity rotates in yaw only; pitch is applied to the camera GameObject
    • Collision: Slides along walls and ceilings via the default collide-and-slide pipeline
    • Input: WASD/ZQSD movement, mouse look, Space to fly up, Left Ctrl to fly down

    Controls

    Input Action
    W / Z Move forward
    S Move backward
    A / Q Strafe left
    D Strafe right
    Mouse Look (yaw + pitch)
    Space Fly up
    Left Ctrl Fly down

    Movement follows the camera look direction — looking down and pressing forward moves the camera downward toward where it is looking.

    How It Works

    Architecture

    The FlyCam follows the same Player → Character entity split as the SinglePlayerSample but is intentionally minimal:

    classDiagram
    direction LR

    class PlayerEntity["Player Entity"] {
        CharacterFollower
        LocomotionInputAsset
        PlayerGameObjectPrefab
    }

    class CharacterEntity["Character Entity"] {
        FlyCamStateMachine
        FlyCamInput
        FlyCamStateData ~yaw~
        FlyCamProfile
        LocomotionVelocity
        LocomotionContact
        PhysicsCollider ~capsule~
    }

    class PlayerGo["PlayerGo (GameObject)"] {
        PlayerGoAuthoring
        PlayerInput
    }

    class CameraTarget["CameraTarget (Transform)"] {
        Camera
    }

    PlayerEntity --> CharacterEntity : CharacterFollower
    PlayerEntity ..> PlayerGo : instantiates at runtime
    PlayerGo --> CameraTarget : child transform

    Rotation: Entity vs Camera

    The entity only rotates around the gravity axis (yaw). This is necessary because the locomotion pipeline applies gravity alignment before the state runs, which would fight with any pitch applied to the entity.

    Pitch is handled entirely on the managed (GameObject) side:

    1. FlyCamPlayerInputAsset.ReadInputsFromAsset accumulates pitch from mouse Y delta
    2. It applies pitch as localRotation on the Camera transform
    3. It passes the pitch angle to the ECS input struct so the state can compute a pitched movement direction
    // In FlyCamPlayerInputAsset — managed side
m_Pitch = Mathf.Clamp(m_Pitch - look.y * LookSensitivity, -MaxPitch, MaxPitch);
m_CameraTransform.localRotation = Quaternion.Euler(m_Pitch, 0f, 0f);
inputs.Pitch = m_Pitch;

    // In FlyCamFlyingState — ECS side (yaw only on entity)
quaternion rotation = quaternion.AxisAngle(up, math.radians(stateData.Yaw));
baseContext.CharacterPosition.Rotation = rotation;

// Pitched forward for movement direction
quaternion pitchedRotation = math.mul(rotation,
    quaternion.AxisAngle(math.right(), math.radians(ctx.Input.Pitch)));
float3 forward = math.mul(pitchedRotation, math.forward());

    Movement Without Gravity

    The state computes desired velocity from input and uses MathematicsHelpers.ComputeAccelerationToTargetVelocity for smooth acceleration/deceleration. No gravity acceleration is applied — both horizontal and vertical channels are purely input-driven.

    The desired direction is split into horizontal and vertical components relative to the gravity axis, then passed to UpdateVelocitiesAndComputeDisplacements with zero gravity contribution.

    Ground Snapping Disabled

    The FlyCamContext partial overrides ComputeGroundSnappingDistance to return zero, preventing the snap-to-ground step from pulling the camera to the floor:

    public partial struct FlyCamContext
{
    public void ComputeGroundSnappingDistance(in FlyCamProfile profile, out float distance)
    {
        distance = 0f;
    }
}

    Stale Contact Clearing

    A flying entity has no transitions to clear the contact state (unlike a grounded character that transitions to Falling). Without clearing, a contact from a previous collision would persist and cause Move() to project displacement incorrectly on subsequent frames.

    The state clears the contact at the start of each integration:

    baseContext.LocomotionContact.ValueRW = LocomotionContact.None;

    The collide-and-slide step will set a fresh contact if a collision occurs that frame.

    Scene Setup

    The sample scene contains:

    1. Subscene with:

      • A character entity (capsule collider) with FlyCamCharacterLocomotionAuthoring — assigns the profile asset and configures the physics capsule
      • A player entity with FlyCamPlayerCharacterAuthoring — references the character, input asset, and PlayerGo prefab

    2. PlayerGo prefab (instantiated at runtime):

      • PlayerGoAuthoring component with Camera and CameraTarget references
      • PlayerInput component bound to FlyCamActionMap
      • A CameraTarget child Transform with the Camera as its child
    Important

    The Camera must be a child of the CameraTarget Transform. The CameraRigFollowControlledCharacterSystem moves the CameraTarget to match the character entity's position. The Camera inherits that position and adds its own local pitch rotation.

    Key Files - Study Order

    Order File What It Teaches
    1 Runtime/FlyCamStateMachine.cs Minimal state machine anchor — single [LocomotionStateMachine] attribute
    2 Runtime/Data/FlyCamInput.cs Input with continuous (Movement, Pitch), accumulated (LookDelta +=), and overwritten (VerticalMovement) fields
    3 Runtime/Data/FlyCamProfile.cs Simple profile with just movement tuning and look sensitivity
    4 Runtime/Data/FlyCamStateData.cs Minimal state data — only yaw angle
    5 Runtime/Data/FlyCamContextExtensions.cs Overriding a DIM default to disable ground snapping
    6 Runtime/States/FlyCamFlyingState.cs Core logic: split yaw/pitch rotation, pitched movement direction, zero-gravity movement, stale contact clearing
    7 Runtime/Data/FlyCamPlayerInputAsset.cs Managed-side pitch handling, camera rotation, Input System action reading

    Things to Try

    1. Adjust fly speed - Open the FlyCamProfileAsset and change Moving > MaxSpeed. Higher values make the camera faster. TimeToMaxSpeed and TimeToStop control acceleration and deceleration feel.
    2. Change mouse sensitivity - Modify LookSensitivity on either the FlyCamProfileAsset (affects yaw) or the FlyCamPlayerInputAsset (affects pitch).
    3. Disable collision - Either set the physics profile's collision filter to collide with nothing in the FlyCamCharacterLocomotionAuthoring inspector, or override OnResolveStateCollisions in FlyCamFlyingState to move the locomotor directly without any collision check. Both approaches help understand what the collide-and-slide pipeline does.
    4. Add a speed boost - Create a second profile with higher MaxSpeed and swap profiles at runtime, or add a sprint input to the action map.

    BehaviorShowCase
    Teaches The controller's behavior envelope — one focused subscene per behavior, loadable at runtime, plus stress-testing tools
    Difficulty Intermediate
    Setup time 2 minutes (open Scenes/BehaviourTests.unity and press Play)
    Dependencies Unity Input System

    What It Contains

    A behavior gallery built around the SimpleCharacter state machine from the SinglePlayerSample. The main scene (Scenes/BehaviourTests.unity) hosts a runtime scene-picker UI; each entry streams in one small subscene that demonstrates a single behavior with a bot-driven character, so you can study or regression-check behaviors in isolation.

    28 behavior subscenes, organized by category under Scenes/BehaviourTests/:

    Category Subscenes What They Cover
    Locomotion 4 Slope grounding, jumping on flat ground, jumping through one-way platforms, stair step-up
    CharacterCollision 3 Head-on character collisions, stacked characters, overlap depenetration
    DynamicBody 7 Pushing light/medium/heavy spheres, sphere-drop impacts at various masses and heights
    DynamicBridge 3 Walking across a dynamic bridge, character and dynamic-body impacts on it
    KinematicPlatform 7 Elevator, conveyor, spinner, one-way platform grounding; crusher, pusher, rotating-bat collisions
    Balance 4 Edge balancing: character vs character and character vs dynamic body, in both directions

    Runtime tools (under Runtime/ and Bot/):

    • TestSceneSelector - UI Toolkit scene picker driven by a TestSceneCatalog asset: hover a category, click an entry to load/unload its subscene. Includes a timestep slider that changes the fixed update rate (Hz) live by writing the FixedStepRate singleton and the FixedStepSimulationSystemGroup timestep (see Fixed Step Rate).
    • Bot input (SimpleCharacterBotAuthoring + SimpleCharacterBotBakingSystem) - bakes a constant Move direction and a one-shot JumpTrigger directly into the character's SimpleCharacterInput, so each subscene's character acts without a player or a runtime input system.
    • SpawningSystem + TestSpawner / SpawnConfig - input-driven stress spawning in seven patterns (sphere, grid, cube, circle, line, random scatter, single-at-click). Tab cycles the pattern, Enter batch-spawns, Shift+LMB spawns one, Backspace clears.
    • GravityWellAuthoring + GravityWellSystem - overrides locomotion gravity for characters within range of a gravity-well entity (per-character gravity demo).
    • PerfTests - Scenes/PerfTests.unity with a PerfSpawner subscene for measuring the controller under large entity counts using the spawn patterns above.

    Things to Try

    1. Compare timesteps - Load KinematicPlatform > Grounding_Elevator and drag the timestep slider from 60 Hz down to 15 Hz to see how the behavior holds up at low tick rates.
    2. Stress-test - Open Scenes/PerfTests.unity, press Enter to spawn a batch, and watch the profiler; press Tab to switch spawn patterns.
    3. Add your own behavior scene - Copy one of the subscenes, modify the setup, and add an entry to the TestSceneCatalog asset so it appears in the picker.

    Museum Tour
    Teaches The controller's whole behavior range in one hands-off pass, plus a runtime application of AI-driven input on streamed-in characters
    Difficulty Beginner to watch, intermediate to read
    Setup time 1 minute (open Scenes/Museum.unity and press Play)
    Dependencies The Behavior Showcase and Single Player samples, imported first

    Where the BehaviorShowCase is a Gym — you pick an exhibit and study it — the Museum is a curated presentation: it picks for you. Press Play, touch nothing, and it cycles all 29 behavior exhibits one at a time, each for exactly as long as that behavior is characterized over, with a placard naming what is on screen. Use it for a first impression, a demo reel, or a five-minute look at what the package does; use the Gym when you want to stop on one behavior.

    Important

    The Museum ships no characters, geometry, or behavior of its own — it streams the Behavior Showcase's subscenes and uses the Single Player sample's reference character. Import both samples before importing this one, or the tour has nothing to show.

    What It Contains

    • Scenes/Museum.unity - the only entry point: a camera framed like the Behavior Showcase's own scene, a directional light, the shared World subscene (physics step + ground plane), and the MuseumDirector GameObject carrying the placard UIDocument.
    • Runtime/Resources/MuseumCatalog.asset - the generated tour data: 29 rows of category, exhibit name, entity-scene reference, and dwell, in tour order. Array order is tour order.
    • MuseumTourSequencer - the tour lifecycle as plain C#: which exhibit is current, whether it is still loading or on display, how much dwell is left, when to hand over. It owns no clock and no world (both the frame delta and "is the exhibit visible yet" are passed in), which is why the whole lifecycle is covered by EditMode tests with no scene and no Play mode.
    • MuseumPlacard - the pure text projection behind the on-screen label: category, exhibit name, and either a whole-second countdown or Loading….
    • MuseumDirector - the only place the sample touches the engine: it streams the exhibit the sequencer asks for, writes the three placard labels, and creates the MuseumTour gate entity.
    • MuseumBotCaptureSystem + MuseumBotReArmSystem - two Burst ISystems that keep the jump exhibits jumping (see Keeping the jump exhibits going).
    • MuseumSampleBuilder (Editor) - regenerates the catalog and the scene from one 29-row table.

    How to Use It

    1. Import Behavior Showcase and Single Player Sample from Window > Package Manager > Samples.
    2. Import Museum Tour from the same list.
    3. Open Scenes/Museum.unity.
    4. Press Play, and do not touch anything — there is no menu, no selection step, and no input path.

    Expected result: within a moment the first exhibit (Locomotion / Jump - Flat Ground) streams in and the placard in the bottom-left reads its category, its name, and a countdown from 3 s. When the countdown runs out that exhibit is unloaded, the next one is loaded, and the placard reads Loading… until it is visible. After all 29 exhibits the tour wraps back to the first and keeps going indefinitely.

    What a common failure looks like: the tour sits on Loading… for 10 seconds and then moves to the next exhibit. That is the deliberate give-up path — an exhibit that cannot be streamed never halts the tour, and it is attempted again on the next lap. If every exhibit does this, the Behavior Showcase sample is not imported, so the scenes the catalog points at do not exist in your project.

    Tour Order and Dwell

    The order is the Gym picker's own order and wording, with Jump - Moving Platform — the one behavior subscene the picker does not list — appended to the end of its category:

    Order Category Exhibits Dwell range
    1 Locomotion 4 3-5 s
    2 Character Collision 3 5-10 s
    3 Kinematic Platform 8 5-30 s
    4 Dynamic Body 7 5-10 s
    5 Dynamic Bridge 3 5 s
    6 Balance 4 10 s

    Each dwell is the duration that scene is characterized over by the golden-master suite, so an exhibit is on display for exactly as long as its behavior is known to be interesting — Jump - Flat Ground for 3 s, Conveyor for 14 s, Crusher for 30 s. Jump - Moving Platform has no characterization run, so the spec mints 8 s for it. One lap is 278 s of dwell (4 min 38 s) plus loading time.

    The dwell clock starts when the exhibit becomes visible, not when it is selected, so streaming time is never charged against the time you get to watch it. Because each handover unloads the previous exhibit and the next lap re-loads it from its baked file, every lap replays each exhibit from its start: the dropped sphere falls again, the stacked characters collide again — you never see a lap of settled leftovers.

    Keeping the Jump Exhibits Going

    Three exhibits are jumps (Jump - Flat Ground, Jump - One-Way Platforms, Jump - Moving Platform). Their characters are bot-driven by the Behavior Showcase's baker, which bakes a one-shot jump trigger — enough for a single jump, which would leave most of a 3-8 s dwell showing a character standing still. The Museum re-arms it, and this is a runtime application of the Switch to AI Input recipe: write the input component directly from a system, and the state machine cannot tell the difference.

    • MuseumBotCaptureSystem runs in InitializationSystemGroup after the scene-streaming group, so it snapshots each streamed-in character's pristine baked JumpTrigger before any tick can consume it. The snapshot lives on the character entity, so it dies with the exhibit and is retaken on the next lap.
    • MuseumBotReArmSystem restores that value once the character reports a ground contact and its trigger has been consumed — one field, one condition, no accumulation.

    Two consequences worth knowing, because they are what keep the exhibits honest:

    • A character with nothing baked is never written to. The snapshot carries no movement and no other intent, so the Museum structurally cannot perform an exhibit that does not jump — what you see on a push, balance, or platform exhibit is the exhibit, not a Museum performance of it.
    • Both systems require a MuseumTour gate entity that only MuseumDirector creates, at runtime, in the Museum scene. There is no authoring component and no baker for it, so with the Museum merely imported and not playing, both systems are inert everywhere else in your project — including in the package's own characterization suites, which reproduce bitwise with the sample installed.

    Regenerating the Sample

    The catalog and the scene are generated, not hand-maintained. MuseumSampleBuilder.TourOrder is the single source of truth for the 29 rows; everything else is derived from it.

    Menu item What it does
    MGM > Museum > Rebuild Catalog Rewrites Runtime/Resources/MuseumCatalog.asset from the tour table, resolving each row to its behavior scene
    MGM > Museum > Rebuild Scene Rebuilds Scenes/Museum.unity (camera, light, World subscene, director + placard panel)
    MGM > Museum > Rebuild All Both, in that order

    All three overwrite in place rather than delete and recreate, so asset GUIDs — and therefore the scene's references — survive a rebuild. Rebuilding the catalog from an unchanged table is a byte-level no-op, which the test suite asserts.

    Things to Try

    1. Change a dwell - Edit the row's DwellSeconds in MuseumSampleBuilder.TourOrder, run MGM > Museum > Rebuild Catalog, and press Play. Watch the placard count down from the new value. (Editing the generated asset directly works too, but the next rebuild overwrites it.)
    2. Reorder the tour - Move a row in TourOrder and rebuild the catalog. Array order is tour order, so the Museum immediately follows the new order — including where the lap wraps.
    3. Watch the re-arm - Let Jump - Flat Ground play and count the jumps in its 3 s. Then open MuseumBotReArmSystem and comment out the re-arm assignment: the character now jumps once and stands still for the rest of the dwell, which is what the one-shot baked trigger does on its own.
    4. Verify the gate - Load a Behavior Showcase subscene from the Gym picker with the Museum sample installed. Nothing jumps by itself: without the Museum scene playing there is no MuseumTour entity, so neither Museum system runs.
